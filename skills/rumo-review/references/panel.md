# Review Panel

Read before a code review or implementation audit by other models: a multi-model panel, or a code second opinion from one named CLI, which is a panel of one lane. The other models review the same target independently through installed agent CLIs; you review it too, then check every finding against the code and write one report. Independence comes from different models, not from assigned personas, and the panel never edits code. Delegated research, design, and open-ended product evaluation use rumo-agent-collaboration instead of this panel.

## When To Run One

- **The user asks:** other models to review code or audit implementation, through several models, the configured reviewers, or a second opinion from a named CLI or model.
- **You propose one** only when both hold. First, a mistake would be costly: the risk gate in `rumo-coding-guidelines` rated the change high, or it is a sizable change to authorization, money, durable data or a migration, concurrency, a public interface, or deployment and infrastructure scripts. Second, at least one of these: its correctness rests on assumptions that tests do not pin, such as a race, a permission edge case, or a compatibility rule; the approach itself may be wrong; or you are not confident, or two fixes for the same problem have already failed. Another model adds most on hidden assumptions and the direction of a change, not on surface bugs, so proposals should be rare. Do not propose one for small or low-risk changes, or when tests and evidence already settle the question.
- **How to propose:** say in one sentence which of those conditions makes this change worth another model's view, which lanes would run, and that they spend quota. `auto_panel` from `agent_config.py lanes review` decides the next step: `ask` asks in one line, `allow` states the lanes and launches, and `off` means no proposal. Propose at most once per target; after the user declines, do not raise it again until the target changes.

## Authorization

Never start another CLI on your own. Before launching, state in one line which lanes will run (CLI, model, effort), what leaves the machine (the diff, the named files, and the repository guidance, sent to each lane's provider), and that each lane spends its provider's quota. Then:

- A request that names the panel or the CLI, the review target, and the scope already supplies agreement; do not ask again for the same scope. So does `auto_panel: allow` for a panel you proposed.
- Otherwise run only after the user agrees to those lanes and that content. Agreement covers this target; ask again for a new target, other lanes, or extra content.
- For an adapter not yet verified, show the command and known limits first. Unverified status alone does not require repeated approval.

## Lanes

- Use the lanes the user names; otherwise run `agent_config.py lanes review`. It and `agent_run.py` live in `../rumo-agent-collaboration/scripts/`, resolved from this skill's directory. Exit 3 means none are configured: ask once which CLI to use and mention that `rumo-setup` saves the choice.
- Prefer providers other than your own; another run of your own model adds little independence.
- Run every lane through `agent_run.py` with `--access read-only`, which checks the CLI itself. If that skill is unavailable, run a CLI directly only after its `--help` confirms a non-interactive mode and a read-only setting; without a confirmed read-only setting, do not use that CLI. A disabled adapter cannot be used, directly or not.
- In Starling, whose sessions have `STARLING_TOOL_TOKEN` in the environment, a lane whose CLI Starling's dispatch accepts for review runs through Starling instead, whose review tier keeps it read-only. Starling runs the CLI's own model, effort, and executable: when the lane names any of them, ask before using Starling. For that lane, launching, waiting, stopping (`starling close`, not `agent_run.py cancel`), and recording (`starling note`, not `agent_run.py record`) follow `../rumo-agent-collaboration/references/starling.md`. Other lanes still run through `agent_run.py`; never replace a lane to fit Starling.

## Run

1. **Target and intent.** Settle the target as SKILL.md describes, then write one paragraph stating what the change is meant to do, from the request, commit messages, and any pull request description. Ask when you cannot tell. Label decisions the user explicitly settled and quote the request or the user's own words as evidence. Label the agent's own conventions and acceptance methods separately. When the target is your own work and fixing it is in scope, first fix the problems you already know about and run the focused checks, so the lanes do not spend quota finding them again; a review-only request changes no code for this.
2. **Brief.** Write one brief for every lane, to a file outside the repository: the intent with the same labels and quotes, the exact diff range and text or named implementation scope, the What To Look For list and Report format from SKILL.md, the lists in [silent-failures.md](silent-failures.md) when the target touches error handling, and where the repository guidance lives. Ask the reviewer to assess how closely the implementation meets the intent. The reviewer may also challenge conventions, decisions, and acceptance methods that the agent set and presented as part of the intent. Report those concerns in a separate **Issues with rules or methods** section outside the severity ranking for implementation findings. Treat decisions the user explicitly settled as fixed. Ask for problems only and accept "no findings" as a valid answer. Withhold the fix history, earlier findings, and your own conclusions. For a diff, start there and open other files to confirm or rule out suspected problems; for an audit, inspect the named implementation and its consumers, even on a clean HEAD. Stay inside that target; you read the surrounding code yourself. Paste whole files only when the read-only sandbox blocks reading, and the diff text whenever it blocks Git.
3. **Launch** every lane at once: `agent_run.py start <cli> --cwd <repository> --prompt-file <brief> --access read-only`, plus the lane's `--model`, `--effort`, and `--executable`. Pass no `--timeout` unless the user names a deadline; never guess a duration. In a client that runs background commands and reports their exit, run each that way. Tell the user the lanes and their run IDs; each lane opens a tab in the `rumo-agents` progress window, and `agent_run.py watch` with no run ID follows every lane on one screen.
4. **Review it yourself** following SKILL.md while the lanes run, and save your findings to a file before reading any lane's output. In a client that cannot report background exits, launch with `--detach` instead, finish your own review, end your turn, and ask the user to tell you when the lanes finish; do not read their live output meanwhile.
5. **Collect.** A lane that fails, times out, returns nothing, or returns something that is not a review is a dropout: record why and continue with the rest. Never retry it on another model or substitute a close one, and never sign in, copy credentials, or change a CLI's configuration on the user's behalf. A dropout is not evidence that the change has no findings. When every lane drops out, say the result is a single-model review. If a CLI edited files despite the read-only setting, stop, report the changed paths, and leave them for the user.
6. **Judge.** Check each implementation finding, yours included, against the code with [judging-findings.md](judging-findings.md). Judge issues with rules or methods by checking where the intent came from, who chose the convention or method, and whether the acceptance evidence proves the intended outcome. Put accepted issues of this kind in the report's **Issues with rules or methods** section, outside the implementation severity ranking. Merge findings that describe the same issue and keep the list of lanes that raised each. Record every run's decision with `agent_run.py record`.
7. **Do not hold the report for the slowest lane.** Once your own review is saved and judged, give the report with the lanes still running marked as pending, so the user can act on it. When a client reports background exits, judge each later lane as it finishes and send the additions; otherwise ask the user to tell you when the pending lanes finish. Stop a lane only when the user asks, with `agent_run.py cancel <run-id>`, and report it as a dropout stopped by the user.

## Report

List implementation findings first, in the severity format of SKILL.md, each with the lanes that raised it. Follow with **Issues with rules or methods** for concerns about agent-defined conventions, decisions, or acceptance methods. Keep those concerns outside the implementation severity ranking. Then include the panel summary below.

- **Lanes:** each lane's CLI, model, effort, run ID, and its number of findings, or its dropout reason.
- **Dismissed:** each dismissed finding, the lanes that raised it, and the file, line, test, or documentation that settles it.
- **Agreement:** where lanes independently agreed, where they disagreed, and what that suggests.

In Loop mode, run a panel in a round only when the user asked for one.
