# Task Flows

Each flow is the default route for one kind of task: when it applies, its steps, which skill owns each step, and where to stop. Pick the flow that matches the request. When a task changes kind midway, such as an investigation the user turns into a fix, switch flows and say so. Skip a step only with a reason you state in the final report.

None of these flows commits, pushes, merges, deploys, or writes to a shared environment on its own; those keep their separate approvals.

## Everyday Work

- **Small edit.** A wording, configuration, or one-place code change with an obvious result. Read the code, make the edit, run the most relevant check, then `rumo-verify`. No plan and no review.
- **Defect fix.** A reported bug the user wants fixed. `rumo-debug` reproduces it and proves the cause; a failing test captures it (`rumo-test`); the fix turns it green and the surrounding tests still pass; the project's verification recipe drives the real feature when one exists; then `rumo-verify`. When the bug will not reproduce, report what was tried instead of patching a guess. After two failed fixes, test the premise ([principles.md](principles.md)).
- **Feature.** New or changed behavior. `rumo-clarify` when the goal or acceptance is unclear, `rumo-plan` when the work spans several steps or modules, the risk gate, thin end-to-end slices that each still work, the verification recipe when one exists, then `rumo-verify`. `rumo-review` only on request.
- **Investigation.** A question about how something works, why it was built that way, or which option to choose. Stay read-only and answer with file, line, and runtime evidence. `rumo-explain` answers how and why questions about the repository's code; `rumo-research` handles technical comparisons and feasibility questions that need evidence before choosing an approach. Simple factual questions need neither workflow.
- **Resume.** Continuing work another session or agent started. When the user names no record, find it with `rumo-handoff`'s Pick Up. Read the handoff document, the plan's decisions and dead ends, or the run record. The record may be another CLI's session, such as one named by `codex resume <id>`: read that session from the CLI's own session files and continue the work yourself; resuming it inside that CLI is delegation, which only the user can ask for. Then check the repository's actual branch, commits, and dirty files against them; name the resume point; then continue under the flow that fits the remaining work. Do not redo work the record shows as done and verified, but do not trust a claim the repository contradicts. A check verified against a goal the user has since changed no longer proves the work done. Treat the record's decisions as `rumo-handoff` Pick Up does, also when the user names the record: carry forward a decision the user confirmed only while its goal and premises still hold, and otherwise report the conflict for the user to decide; re-check a decision the record does not show the user confirming, and ask the user to confirm it before building on it.
- **Backtrack.** The current approach rests on something that turned out wrong: the user says the direction is wrong, or a premise of the approach, plan, or decision is disproved. Stop widening the change. Steps 1 to 3 are read-only; the authorization limits are in SKILL.md under Authorization.
  1. State in one or two sentences what overturned the route, the evidence or the user's changed goal, and which check will prove the correction.
  2. Find the last point with evidence that it met the current requirement, and say what that evidence checked. When no such point exists, say so and propose the smallest reproducible state to rebuild from and the check that will verify it; do not build it yet.
  3. List the changes that depend on the overturned premise and any rebuild from step 2, then stop and ask the user which to undo or rebuild, and whether to retry.
  4. After the approved undo or rebuild, read the diff and rerun the check that verified the restore point, or for a rebuild the check proposed in step 2. Report what was undone, what was kept, and which behavior the check covers; a check that covers only part of the overturned work does not show the whole tree is back. A rebuilt state stays unverified until a check against the current requirement passes. When the user approved only the undo, stop here.
  5. When the user approved a retry and a plan file exists, append the dead end to its decisions and dead ends (`rumo-plan`) before the retry starts, so whoever retries sees it.
  6. Retry in this session unless the user agrees to a fresh session or another agent; another agent goes through `rumo-agent-collaboration`, and a fresh session starts from a resume note written with `rumo-handoff`. Give whichever runs it only the current goal, constraints, a minimal reproduction, and verified facts. A retry in this session still carries the earlier context; say so.

  The task is corrected only when a check that tells the new route from the old one passes against the current requirement.
- **Refactor.** A change to structure that must keep behavior. Confirm that existing tests cover the behavior being moved, and add characterization tests first when they do not; move in small steps that keep those tests green; rerun the same tests unchanged at the end. Delete the old path once every caller has moved instead of keeping both. See Delete Before Adding and Keep The Reader's Load Small in [principles.md](principles.md).

## Measurement

- **Performance problem.** Something is too slow or uses too much memory. Read [measurement.md](measurement.md) before the first baseline run. Measure a baseline with fixed data, environment, and command; find the hot path with a profiler or trace; fix it; measure again the same way and report both numbers with the method. Repeat the measurement when the numbers vary between runs. Never claim it got faster without a measurement taken the same way before and after. Check the numbers against [measurement.md](measurement.md) before reporting them.
- **Metric improvement.** Sustained work to move one number toward a target, such as start-up time or bundle size. Fix the measurement first, check it against [measurement.md](measurement.md), and show that it detects a change; record every attempt as one line in the plan's decisions and dead ends, with the hypothesis, the change, the before and after values, and whether it was kept or reverted; revert any attempt that does not help. Stop when the target is met or the remaining ideas are not worth their cost. Never loosen the target to declare success.

## Diagnosis And Exploration

- **Runtime diagnosis.** A leak, a busy loop, a visual glitch, or a profile, trace, or heap snapshot captured earlier. Capture the live signal or read the artifact, narrow it to one mechanism, confirm the mechanism with added logging or a probe, and map it to a source file and line (`rumo-debug`). This flow ends with a diagnosis; a fix needs its own request.
- **Prototype.** A cheap, throwaway build to make one design or behavior decision. Name the decision first. If you cannot name the decision, it is not a prototype; use the feature flow. Build outside the product source tree with the lightest stack that shows the idea; put alternatives behind one switch and make uncertain parameters adjustable; observe or screenshot each variant; recommend one. Prototype code never enters the product: the chosen direction is built again under the feature flow.
- **Visual parity.** Making a UI match another implementation, or migrating its styling, without visible change. Capture baseline screenshots of every state before changing anything, migrate one component at a time, and compare each against its baseline; investigate any nonzero difference (`rumo-frontend`). Never edit the baseline or the comparison tool to make a diff pass; if the baseline looks wrong, stop and ask.

## Repository Workflows

- **Skill or prompt change.** Editing a `SKILL.md`, agent instructions, or a prompt. Write it with `rumo-prose`, run the repository's validators and focused regression checks, and follow the repository's acceptance policy for real-client trigger or behavior evaluations. Keep the risk gate and report any missing required evidence; do not make paid evaluations mandatory beyond that policy or the user's request.
- **Pull request follow-up.** Only when the user asks to watch or fix an open pull request (`rumo-git-commit`). Resolve conflicts first, then review comments, then failing checks; classify a failure before rerunning it. Never merge the pull request or mark it ready.
- **Pause.** The user stops the work, or the session must end before the task is done. Finish or back out of the current step and start nothing new; take no irreversible action to pause. Write a resume note with `rumo-handoff` when the user wants one, or report the state in the final message. Leave the changes as they are; commit only when the user asks. A request to wrap up ("收尾") follows Wrap Up in `rumo-handoff` instead.
